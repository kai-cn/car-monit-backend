# 双端接口全量对比校验（2026-11-02，第三轮：共用 MySQL + 独立 Redis DB）

> 目标：从头重做 Java(9988) 与 Go(9989) 的逐接口校验。本轮与前两轮的差别是
> **两端使用不同的 Redis DB**，缓存不再互相覆盖，因此可以单独验证「缓存串号」
> 并把之前被共享状态掩盖的差异暴露出来。所有校验脚本已进仓库（`scripts/parity/`）。

## 1. 环境矩阵

| 项 | Java | Go |
|---|---|---|
| 进程 | `ruoyi-admin/target/ruoyi-admin.jar --server.port=9988`（复用已在跑的进程，未重启） | `bin/carmonit-server.exe`，`configs/config.yaml` |

| 账号 | admin / Admin@2025-（登录需验证码，答案在 db0 的 `captcha_codes:<uuid>`） | admin / Admin@2025-（无验证码） |

Redis DB 选择：db1 已被其它移植端占用（1274 个键，`sys_dict:*`/`gantry_list` 等），
为避免干扰，Go 使用干净的 **db2**。

配置修改点（`configs/config.yaml`）：

```yaml
redis:
  host: 127.0.0.1
  port: 6379
  password: ""
  database: 2      # Java 用 0；两端缓存互不可见
```

`spring.redis.database: 0` 保留为 Java 原配置的对照展示，运行期不读取（`config.go` 只读顶层 `redis` 段）。

### 环境层面的两个坑（写在这里避免重复踩）

- **MSYS 路径改写**：Git Bash 会把 `/manager` 之类的参数变成交付路径（`D:/work/Git/manager`），
  所有对比命令必须带 `MSYS2_ARG_CONV_EXCL='*'`，否则前缀匹配不到任何路由（表现为 total=0）。
- **CRLF**：仓库 `core.autocrlf=true`，工作区 Go 文件是 CRLF，`gofmt -l .` 会把每个文件都列出来。
  真正的格式检查要在 LF 归一化后的副本上做：
  `git diff --name-only HEAD -- '*.go' | xargs -I{} sh -c 'tr -d "\r" < {} > /tmp/f.go && gofmt -l /tmp/f.go'`。

## 3. 阶段结果一：路由清单全覆盖

`routes.py` 扫描 82 个 Java 控制器与 Go 启动日志的注册结果（占位符与末尾斜杠归一后比较）：

| 指标 | 数值 |
|---|---|
| Java 路由 | 511 |
| Go 注册路由（修复后） | 514 |
| 匹配 | 511 |
| **Java 有 / Go 没有** | **0** |
| Go 有 / Java 没有 | 3（`GET /healthz`、`HEAD /`、`OPTIONS /`） |

修复前是 13 条 Java 有而 Go 没有，逐条如下（这也是本轮的一批真实缺陷）：

| 缺失端点 | Java 依据 | 处理 |
|---|---|---|
| `GET /system/user/` | `SysUserController:174 @GetMapping(value={"/", "/{userId}"})`，前端 `getUser('')` 走带斜杠地址 | 注册 `g.GET("/", Perm("system:user:query"), GetInfo)`；第二轮误删的是这个变体 |
| `POST/PUT/DELETE/PATCH /` | `SysIndexController:24 @RequestMapping("/")`（不限方法） | `engine.GET("/", …)` 改为 `engine.Any("/", …)` |
| `/oss/bucket`、`/oss/bucket/{b}`、`POST/DELETE /oss/bucket/{b}`、`POST /oss/object/{b}`、`POST/GET /oss/object/{b}/{o}`、`GET /oss/object/{b}/{o}/{expires}`、`DELETE /oss/object/{b}/{o}/` | `OssEndpoint.java:26-114`（`@RestController @RequestMapping("/oss")`，未迁移） | 新增 `internal/modules/systemaux/oss_endpoint.go`，用已有的 minio-go 客户端实现九个动作 |

Go 侧多出的 3 条为有意差异：`/healthz` 是存活探针；`HEAD /`、`OPTIONS /` 由 Gin 的 `Any`
连带注册（Spring 对 `@RequestMapping` 也隐式支持 HEAD/OPTIONS）。

## 4. 阶段结果二：本轮新发现并修复

| # | 现象 | 根因（Java 依据） | 修复 |
|---|---|---|---|
| 1 | `POST /login` 后 Go 侧没有登录日志 | Go 把语义串 `Success` 直接写进 `sys_logininfor.status`（`char(1)`），MySQL 报 `Data too long`，整行丢失。Java 在 `AsyncFactory.recordLogininfor:71-80` 先映射成 `Constants.SUCCESS="0"`/`FAIL="1"` | `internal/auth/service.go` 新增 `logininforStatus()`，写库前映射；未知语义值→ NULL（与 Java 一致） |
| 2 | `GET /system/user/` 404；`GET /system/user` 却返回 200 载荷 | Spring 把 `"/"` 注册成 `/system/user/`，精确路径 `/system/user` 上只有 POST/PUT ⇒ GET 命中 `HttpRequestMethodNotSupportedException` | 带斜杠注册 `GetInfo`；不带斜杠注册 `MethodNotAllowed` 返回 `{code:500, msg:"Request method 'GET' not supported"}` |
| 3 | `/oss/**` 8 个端点 Go 完全没有 | `OssEndpoint` 未迁移 | 新增 `oss_endpoint.go` 并在 `systemaux/register.go` 挂载；成功返回裸 SDK JSON（无 AjaxResult 信封），删除返回 202 空体，异常走 `{msg, code:500}` |
| 4 | `/oss/bucket` 在 Go 侧要 210 秒才失败，Java 11.5 秒 | minio-go 沿用 OS TCP 超时（Windows ≈21s）再乘内部重试 | `newOssStorage` 给 Transport 设 3s 连接超时（只限建连，不影响慢但正常的传输），实测降到 30s |
| 5 | `incomeStatics`/`concernedList`/`exceptRecordList` 返回全量，Java 返回 10 条 —— 顺带专项排查发现**共 45 个端点**都有这个问题 | `TableSupport.getPageDomain` 对缺省参数取 `pageNum=1、pageSize=10`，凡调用 `startPage()` 的端点在请求不带分页参数时也只返回一页 | 新增 `web.PageAlways(c)`；把所有「Java 侧 startPage」的列表路径改成它（base/manager 的通用 `respondList`、car_track、car_free、quartz、ops 登录/操作日志、systemaux 参数/字典/公告/文件/首页菜单、generator 等）；导出与 `listAll`（Java 不分页的那些）仍用 `web.Page(c)` |

另有两项属于上一轮已修、本轮复核仍成立：`sys_dict` 缓存值的 `params` HashMap 强制标记、
FastJson2 值的 `@type`/`L`/`Set` 兼容读写。

### 4.1 默认分页专项（`check_default_page.py`）

前几轮的 GET 对比都是带 `?pageNum=1&pageSize=3` 跑的，因此「不带分页参数时 Java 仍分页」这一类
差异被完全掩盖。本轮改为**从 Java 源码里把所有调用 `startPage()` 的 GET 路由抽出来**（96 条），
在不带任何分页参数的前提下逐条比对两端的 `rows` 数量与 `total`：

| 阶段 | 比对 | 不一致 |
|---|---|---|
| 修复前 | 90 | **42** |
| 修复后 | 91 | **0** |

（`total` 两端始终一致，说明 Go 的 COUNT 逻辑本来就对，缺的只是 LIMIT。）
跳过的 18 条是导出类（返回二进制）与少量需要真实业务主键才能命中的路径。

## 7. 阶段结果五：Redis 双 DB 隔离校验

`check_redis_isolation.py`，**24 项断言全部通过**（`p3_isolation.log`），测试行/测试键无残留：

| 组 | 断言 |
|---|---|
| 登录态 | Go 的 `login_tokens:*` 只出现在 db2、Java 的只在 db0；两端原值都带 `@type` |
| sys_config | Go 写 ⇒ 缓存落在 db2、db0 无此键；Java 写 ⇒ 反之；**对端无缓存时回源共享 MySQL 读到同值**；删除后各自的缓存被驱逐 |
| sys_dict | Java 读只写 db0；Go 读写 db2 且不改动 db0；两端缓存值都带 `SysDictData` 标记；两端响应逐字段一致 |
| 对象缓存 | Go 新增白名单 ⇒ `white_car_list` 在 db2 出现该行，且 db0 的值逐字节未变 |

## 8. 剩余差异定性

15 条 GET 差异 + 8 个写资源，分三类。**本轮没有一条差异属于「Go 行为写错」**。

### 8.1 由本轮「独立 Redis DB」设定本身造成的差异（2 条，非缺陷）

| 接口 | 现象 | 说明 |
|---|---|---|
| `/monitor/online/list` | Java 55 行 / Go 17 行，行内字段结构一致 | 各端只看得见自己 DB 里的会话；这正是隔离要求的效果（§7 已验证两端不会互写） |
| `/monitor/cache` | `commandStats`、键数量不同 | 统计的是各自 DB 的运行态数据 |

### 8.2 Java 侧自身缺陷（Go 保持可用）

| 接口 | Java 现象 | Java 依据 |
|---|---|---|
| `/system/upgradeInfo/{list,newest,export,{id}}` | 500 表不存在（两侧都 500，错误文本不同：MyBatis 长文本 vs 驱动文本） | 本地基线库无 `sys_upgrade_info` |
| `/base/geometry/syncAllGeometry` | 同上 | 缺 `geometry_copy1` |
| `/base/fitting/list` | `ReflectionException` | Mapper 引用实体上不存在的 `id` 属性 |
| `/base/feeGantry/{id}`、`/base/snapshotflow/{id,earliest-time}` | `String cannot be cast to ...` | 外部 9901 服务返回的 `Map`/`String` 被强转成实体 |
| `/base/feerecords/{id}`、`/base/feestationexit/list` | `HTTP 500` / `SocketException` | 转发外部 9901 服务的 proxy |
| `/monitor/jobLog/{id}` | 500 缺少必需的路径变量 `[jobLogId]` | 编译未保留参数名 |
| `/monitor/server` | 500 `NoSuchMethodError: com.sun.jna.Memory.close()` | JNA 版本冲突 |
| `POST /system/user` | 任意请求体都 `IndexOutOfBoundsException: No group 2` | `SqlLogInterceptor:265` 用 `sql.replaceFirst("\\?", paramValue)`，BCrypt 串里的 `$2a$` 被当成正则分组引用 |
| `POST /base/{section,toll,gantry}`、`/base/org`、`/manager/carsuspiciousback` | `Column 'id'/'big_id' cannot be null` | `IdType.INPUT` 且服务层不生成主键 |
| `POST /base/configServiceArea` | `Unknown column 'id' in 'field list'` | 实体声明了库里不存在的 `id` |
| `DELETE /base/geometry/{ids}` | `Unknown column 'del_flag' in 'field list'` | `GeometryMapper.xml` 逻辑删除引用不存在的列 |

### 8.3 非 JSON 附件流（24 条）

Excel/Word/图片二进制由 POI/EasyPOI 与 excelize 生成，无法逐字节一致；表头、列顺序、
文件名信封（`UUID_表名.xlsx`）已按 Java 注解对齐，Go 侧统一按「能下载、列对得上」验收。

### 8.4 遗留待办

- `/oss/**` 九个端点的**成功**返回形态尚未核对：`oss.endpoint=172.30.100.102:9002` 的 MinIO 在本环境不可达，
  两端都只能观察 500 信封一致性（`check_oss.py` 已通过）。等有可用 MinIO 时再逐字段比一次。
- Go 失败耗时 30s 仍大于 Java 的 11.5s（建连超时 3s × minio 内部重试）。若要进一步贴近，
  可把重试次数也限掉，但对可达的 MinIO 无收益，暂不处理。
