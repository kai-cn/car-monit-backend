# 双端接口全量对比校验（2026-11-02，第三轮：共用 MySQL + 独立 Redis DB）

> 目标：从头重做 Java(9988) 与 Go(9989) 的逐接口校验。本轮与前两轮的差别是
> **两端使用不同的 Redis DB**，缓存不再互相覆盖，因此可以单独验证「缓存串号」
> 并把之前被共享状态掩盖的差异暴露出来。所有校验脚本已进仓库（`scripts/parity/`）。

### 环境层面的两个坑（写在这里避免重复踩）

- **MSYS 路径改写**：Git Bash 会把 `/manager` 之类的参数变成交付路径（`D:/work/Git/manager`），
  所有对比命令必须带 `MSYS2_ARG_CONV_EXCL='*'`，否则前缀匹配不到任何路由（表现为 total=0）。
- **CRLF**：仓库 `core.autocrlf=true`，工作区 Go 文件是 CRLF，`gofmt -l .` 会把每个文件都列出来。
  真正的格式检查要在 LF 归一化后的副本上做：
  `git diff --name-only HEAD -- '*.go' | xargs -I{} sh -c 'tr -d "\r" < {} > /tmp/f.go && gofmt -l /tmp/f.go'`。

### 4.1 默认分页专项（`check_default_page.py`）

前几轮的 GET 对比都是带 `?pageNum=1&pageSize=3` 跑的，因此「不带分页参数时 Java 仍分页」这一类
差异被完全掩盖。本轮改为**从 Java 源码里把所有调用 `startPage()` 的 GET 路由抽出来**（96 条），
在不带任何分页参数的前提下逐条比对两端的 `rows` 数量与 `total`：

| 阶段 | 比对 | 不一致 |
|---|---|---|
| 修复前 | 90 | **42** |
| 修复后 | 91 | **0** |

（`total` 两端始终一致，说明 Go 的 COUNT 逻辑本来就对，缺的只是 LIMIT。）
跳过的 18 条是导出类（返回二进制）与少量需要真实业务主键才能命中的路径。

### 4.2 查询参数矩阵（`check_query_matrix.py`）

对 25 个代表端点跑参数组合（分页越界、`pageSize=0/-1/99999`、`orderByColumn` 合法与非法、
`isAsc` 乱值与别名、`reasonable=false` 的两种越界角，再加各自的过滤条件），逐字段比对：

| 阶段 | 组合数 | 有差异的组合 |
|---|---|---|
| 修复前（11 种组合） | 696 | **183** |
| 分页语义 + 客户端排序 + hutool null 修复后 | 696 | **3** |
| 再加 PageHelper 空结果短路（§4 第 9 项） | 696 | **0** |
| 补 5 种组合 + 修掉脚本自身的盲区（16 种组合） | 1155 | **24**（全部是 §4 第 11/12 项） |
| 排序覆盖与 afterCount 对齐后 | 1155 | **0**（另 73 组「已知有意差异」，见下） |
| 再补 `reasonable` 两种取值 + 修 §4 第 14 项 | **1309** | **0**（已知有意差异仍 73 组） |
| 再补 `pageSize=0/-1 × orderByColumn` + 修 §4 第 15 项 | **1463** | **0**（已知有意差异仍 73 组） |

两次扩容都各自挖出了真缺陷，过程记录如下：

1. **696 → 0 之后不能收工**。原来的组合表里 `isAsc=bogus` 从不与 `orderByColumn` 同时出现，
   `reasonable=false` 也从不与越界页码同时出现，两个盲区正好对应 §4 第 10、13 两项。
2. **脚本自身有盲区**：`check_query_matrix.py` 原来写的是
   `if "rows" not in a: continue` —— Java 返回错误信封（没有 `rows` 键）的组合被**静默跳过**，
   于是 `/monitor/{operlog,logininfor}/list?orderByColumn=...` 这类「Java 500、Go 200」永远报不出来。
   改成：两端都是 TableDataInfo 时逐字段比，否则只比信封（错误文本按 §8.2 认定不同），
   并单独统计「已知有意差异」。
3. **`orderByColumn=1;drop` 这类注入探测**计入 73 组已知差异：Java 的
   `SqlUtil.escapeOrderBySql` 抛 `UtilException("参数不符合规范，不能进行查询")` → code=500；
   Go 拦掉非法字符后**忽略该排序**继续正常返回。两边都不会注入成功，Go 不返回 500 是有意的保守选择。
4. 之前那 2 条 `/base/geometry/list` 的定位过程：起初以为只是「两端都 500、错误文本不同」，
   单独复现才发现 Java 其实是 **200/total=0** —— `geometry` 表没有 `create_time` 列，
   而 `lxbh=G` 让 count 归零，PageHelper 因此没有执行带非法 ORDER BY 的数据查询（§4 第 9 项）。
5. `/monitor/operlog/list?pageSize=99999` 出现过两端 total 差 1：是比对期间请求自身在写操作日志，
   数据在长，复跑即消失（不是逻辑差异）。
6. 第 14 项（`reasonable` 词表）不是矩阵先报出来的，而是补单测时逐行读 `Convert.toBool` 发现的：
   原来 Go 只认字符串 `"true"`，而 Java 认 `true/yes/ok/1`，且乱值会回落成 TRUE。
   实测 `/manager/carinfo/list?pageNum=9999&pageSize=3&reasonable=1`：Java 回末页给 2 行，
   Go 当时按 false 给了 0 行 —— 立刻补进矩阵组合，避免下次再靠肉眼。

这一类差异在之前的固定带 `?pageNum=1&pageSize=3` 的对比里**完全看不见**，
说明「参数面」必须单独覆盖，不能只比默认请求。

### 4.3 PageHelper 语义对照（`SkipQuery` 一类改动的源码依据）

本轮所有分页相关改动都以本地依赖的真实源码为准（`pagehelper-spring-boot-starter 1.4.7`
→ `pagehelper 5.3.3`，从 `.m2` 里的 `-sources.jar` 解出，不是凭记忆）：

| Java 源码位置 | 语义 | Go 落点 |
|---|---|---|
| `PageInterceptor.java:137-145` | `beforeCount` 通过后执行 count；`afterCount` 返回 false 时 **`return dialect.afterPage(new ArrayList(), …)`** —— 数据查询一次都不执行 | `web.PageDomain.SkipQuery(total)`，15 处分页执行器（11 个文件）先问这一句 |
| `AbstractHelperDialect.java:86-107` | `afterCount` 先 `page.setTotal(count)`；**`pageSizeZero=false`（`application.yml` 未配置该项，取 PageHelper 默认）⇒ `pageSize<=0` 一律不放行**；否则放行条件为 **`page.getPageNum() > 0 && count > page.getStartRow()`** | `SkipQuery` 两条都照抄；`Page()` 把负页长归一为 0 只是 `LIMIT ?` 的保险，正常路径不再触达 SQL |
| `Page.java:221-239` | `setTotal` 里算 `pages=ceil(total/pageSize)`，`reasonable && pageNum>pages` 时回末页（`pages==0` 不改页码） | `Clamp(total)` 的上界分支 |
| `Page.java:245-256`、`:365-369` | `setReasonable`/`pageNum()`：**只有 reasonable 为真**才把 `pageNum<=0` 拉回 1 | `Clamp(total)` 的下界分支（原来无条件拉回 1，就是 §4 第 10 项的差异） |
| `Page.java:345-348` | `calculateStartAndEndRow`：`startRow = pageNum > 0 ? (pageNum-1)*pageSize : 0` | `startRow()` / `Offset()` |
| `AbstractHelperDialect.java:188-191` + `OrderByParser.java:54-73` | 客户端给了 orderBy：`converToOrderBySql` **剥掉语句最外层的 order by**，再拼 `order by <客户端>`（原 order by 含 `?` 时抛 `PageException`） | `manager.orderFor` / `base.orderByFor` / `ops.orderFor` / `system.orderByOr` / `systemaux.queryPage`（语句自带排序一律改成经 defaultOrder 传入） |

### 8.4 有意保留的差异（不修）

| 现象 | Java 行为 | Go 行为 | 理由 |
|---|---|---|---|
| `orderByColumn=1;drop` 这类含非法字符的排序列 | `SqlUtil.escapeOrderBySql` 抛 `UtilException` → `code=500`、`msg="参数不符合规范，不能进行查询"` | 拦掉非法字符后**忽略该排序**，正常返回数据 | 两边都注入不成功；Go 不因探测请求把列表打成 500。矩阵里这类组合单独计为「已知有意差异」（73 组） |

| `DECIMAL(m,2)` 金额列的字面量位数 | Jackson 按 `BigDecimal` 原样输出 `67.00`、`111.00` | Go 扫进 `float64` 后输出 `67`、`111`（`0.33` 这类非整值两边一致） | 数值相等；`pp.norm` 按数值比较所以 GET 专项不报，只有写生命周期专项（类型更严）报出 1 条。要逐字面对齐得把每个金额字段换成保留标度的原始字面量类型，涉及上百个字段与 GORM 扫描，风险远大于收益 |
