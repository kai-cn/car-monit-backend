# Java 后端项目 1:1 像素级移植为 C++ 的 执行提示词

> 用途：用于将 Java 后端项目按行为一致性、接口一致性移植为最新主流生产版本 C++ 实现，并生成 Java → C++ 逐层对照说明、可运行代码与启动闭环文档。
>
> 目标读者：原 Java 开发人员。
>
> 核心目标：让 Java 开发人员能逐层对照、快速定位、理解差异，并成功启动 C++ 版项目。

---

你是一名同时精通 Java 企业级后端与现代 C++ 生产开发的技术架构师。我有一个 Java 后端项目，需要**以 1:1 像素级的行为一致性和接口一致性**移植为 C++ 实现，目标是最新主流生产版本（C++20/23 + CMake + Conan/vcpkg）。原 Java 开发人员后续要阅读并维护 C++ 版代码，因此你的核心交付物不是“一份能跑的 C++ 代码”，而是一套**让 Java 开发人员能逐层对照、快速定位、理解差异、并成功启动项目的完整映射说明 + 可运行代码**。

**硬性约束：**

- 对外暴露的 API 路径、请求/响应 JSON 结构、状态码、错误码、字段语义、分页规则、鉴权头名称、超时行为、重试语义，必须与 Java 版逐字节、逐语义一致。如果 C++ 生态无法做到完全一致，必须显式标出“行为差异点”并给出补偿方案。
- 必须包含**完整的构建、依赖安装、配置、启动、健康检查**步骤。Java 开发人员拿到 C++ 项目后，应能仅凭你的说明从零启动，不需要额外追问。
- 不得用“C++ 没有对应物”直接跳过。Java 框架/中间件必须给出 C++ 生产级替代候选，并说明取舍依据。

## 第一步：建立“Java 组件 → C++ 组件”映射矩阵

先对原 Java 项目做一次技术栈扫描，列出用到的框架、中间件、库和运行时机制。对每一项，在 C++ 侧给出**至少一个生产级候选**，并说明选择理由和已知行为差异。以下映射关系可作为分析起点，但必须结合原项目实际依赖逐项核对，不得直接套用：

| Java 侧                                                  | C++ 生产候选                                                 | 关键差异与核查要点                                           |
| -------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| Spring Boot / Spring MVC（Web + REST + 路由 + 参数绑定） | Paozhu（定位为“C++ 领域的 Spring Boot”，全栈、注解式路由、内置 ORM，适合企业级 CRUD）；Drogon（高性能异步，Reactor + 非阻塞 I/O，TechEmpower 实测 545,443 RPS） | Spring 的自动配置和约定优于配置在 C++ 侧通常不存在；路由声明方式、中间件顺序、参数校验时机需要逐项对齐 |
| Hibernate / JPA / MyBatis（ORM + 数据库访问）            | Drogon ORM、SOCI、ODB、SQLPP11                               | 懒加载、一级/二级缓存、脏检查、事务传播语义在 C++ ORM 中通常不完整；需要标注哪些 JPA 行为被显式实现、哪些被放弃 |
| Spring DI / IoC（@Autowired / @Component）               | Boost.DI、Hypodermic                                         | C++ 没有运行时类路径扫描；Bean 生命周期、作用域（singleton/prototype）需要以显式注册或工厂方式重建 |
| Spring Security / JWT / 过滤器链                         | Drogon JWT middleware、jwt-cpp、oat++ Auth                   | 过滤器链顺序、认证失败后的响应形态、CORS 默认行为需要手动对齐 |
| application.yml / properties                             | yaml-cpp + nlohmann/json（或仅 yaml-cpp）                    | Spring 的配置优先级、profile 激活、@ConfigurationProperties 松散绑定在 C++ 侧需要显式编码；环境变量覆盖、命令行覆盖的优先级必须显式定义 |
| SLF4J / Logback / Log4j2                                 | spdlog（fmt 格式化、异步线程池、滚动 sink 完善）；glog（Google 风格，同步缓冲） | 日志格式字符串、MDC/上下文传递、按级别分流到不同文件的行为需要逐项配置对齐 |
| Jackson（JSON 序列化/反序列化）                          | nlohmann/json（开发效率优先，STL 风格）；RapidJSON（低层控制、in-situ 解析、性能优先） | 空值处理、日期格式、枚举序列化、未知字段策略（FAIL_ON_UNKNOWN_PROPERTIES）必须逐字段对齐 |
| Dubbo / Feign / OpenFeign（RPC 与服务调用）              | gRPC（跨语言、HTTP/2、云原生首选）；Thrift（纯 TCP、多协议、适合高性能 C++ 服务）；Tars（C++ 原生生态） | Dubbo 的服务治理、负载均衡策略、超时重试语义在 gRPC/Thrift 中需要以拦截器或 sidecar 方式重建；接口 IDL 需要从 Java 接口反向生成或手动定义 |
| JUnit 5 + Mockito                                        | GoogleTest / Catch2 + FakeIt                                 | Mock 的静态方法、final 类在 C++ 中无法直接 mock；需要提前识别哪些测试策略不可迁移 |
| Maven / Gradle                                           | CMake + Conan / vcpkg                                        | 传递依赖解析、版本对齐、打包产物形态完全不同；需要输出精确的 CMakeLists 和 conanfile/vcpkg.json |
| JVM（GC、线程池、类加载）                                | 无直接对应；std::thread/jthread、线程池库、Boost.Asio        | 这是**最大的非对称差异**。Java 开发人员习惯的“不用管内存”“不用管线程生命周期”在 C++ 中全部变为显式责任，必须在说明中重点标注 |
| Javadoc                                                  | Doxygen                                                      | 注释格式和生成流程需要替换                                   |
| Spring Actuator                                          | Drogon 内置健康检查端点 / 自定义 REST                        | 端点路径、返回 JSON 结构需要手动对齐，不能假设开箱一致       |

## 第二步：按“层”做 1:1 对照，而不是按“文件”翻译

不要逐行翻译 Java 文件。按以下层次组织对照说明，每一层都给出**Java 侧写法 → C++ 侧写法 → 行为一致性判断 → 差异补偿**：

### 2.1 语言与运行时层

重点解释 Java 开发人员最不熟悉的非对称差异：手动内存管理（`new/delete`、所有权、`unique_ptr/shared_ptr`）、指针与引用、值语义 vs 引用语义、对象生命周期、编译链接模型、模板实例化、`const` 正确性、移动语义。这一层不是“翻译”，而是“帮助 Java 开发人员建立正确的心智模型”。

### 2.2 请求处理与路由层

对齐 URL 映射、HTTP 方法、路径参数/查询参数/请求体的绑定规则、Content-Type 处理、参数校验失败时的状态码和错误体结构。如果 Java 侧依赖 Spring 的 `@Valid` + `BindingResult`，C++ 侧是手动校验还是框架校验，必须写清楚。

### 2.3 序列化与契约层

逐字段列出请求/响应 DTO 的映射。Jackson 的 `@JsonProperty`、`@JsonIgnore`、`@JsonFormat`、空值策略，在 nlohmann/json 或 RapidJSON 中分别如何实现。如果字段名、日期格式、枚举值有任何偏差，必须标出。

### 2.4 数据访问与事务层

Java ORM 的哪些行为被保留、哪些被降级为手写 SQL。事务边界、隔离级别、回滚条件、连接池配置在 C++ 侧的等价物。如果无法保持 JPA 的懒加载语义，必须说明对业务代码的影响。

### 2.5 横切关注点层

日志、鉴权、异常处理、限流/熔断、指标埋点、配置刷新。每一项给出 Java 的机制、C++ 的实现方式、以及“看起来一样但实际不一样”的陷阱。例如：Java 的 `ThreadLocal` 在 C++ 中通常需要显式传递上下文或使用协程局部存储。

## 第三步：确保“可启动”的闭环说明

这是验收的硬标准。必须输出以下内容，且顺序可执行、无隐含前提：

1. **环境要求**：编译器及最低版本、CMake 版本、包管理器（Conan/vcpkg）及配置方式、操作系统假设。
2. **依赖安装**：逐条可复制粘贴的命令，包括系统包、Conan remote 或 vcpkg triplet。
3. **构建命令**：从零开始的完整 `cmake` + `build` 命令，Debug 和 Release 各一套。
4. **配置准备**：C++ 版配置文件的路径、格式、必填项、与 `application.yml` 的字段对照表；环境变量覆盖方式。
5. **启动命令**：前台启动、指定配置文件、指定端口、日志输出位置。
6. **验证启动成功**：健康检查端点或可调用的最小 API 示例（`curl` 命令 + 预期响应）。如果依赖数据库，需要说明如何初始化或 mock。
7. **常见启动失败排查**：至少列出 3 种最可能出现的启动错误（链接错误、配置项缺失、端口占用、依赖版本冲突）及对应的检查命令。

## 第四步：标记“高风险差异点”

在输出末尾单独列一节“Java 开发人员必须警惕的 10 个非对称差异”，按风险从高到低排序。重点关注：

- 内存所有权：C++ 对象何时析构、谁负责释放、`shared_ptr` 循环引用。
- 线程模型：Java 线程池 + 阻塞调用的直觉，在 C++ 异步框架中可能导致阻塞事件循环。
- 异常安全：C++ 析构函数中不能抛异常；部分框架以错误码代替异常。
- 编译期约束：模板错误信息、链接顺序、ODR 问题，对习惯 JVM 热部署的开发者是全新体验。
- 空值语义：Java `null` 与 C++ `std::optional`、空指针、空字符串的区别。
- 序列化默认值：Jackson 与 nlohmann/json 对缺失字段、null、默认值的处理差异。
