## 四、任务3/4 修复（backend，已改本地待提交）

### 4.1 backend cd-standalone verify 两个失败根因（run `44346217461`）

- **verify(py)**：`python3.11 -m zipfile -l "$whl" | head -10`，head 读满 10 行提前关闭管道，`zipfile.printdir()` 继续 print 抛 `BrokenPipeError`，job exit=1。实测复现：head 方式 python 侧 exit=1，sed 方式 exit=0。修复：改用 `sed -n '1,10p'`（读完全部输入再输出，不触发 SIGPIPE）。
- **verify(java)**：Spring Boot 用 `--spring.main.web-application-type=none` 启动，logback.xml 把日志写到 `/home/ruoyi/logs`，容器内目录不存在导致 RollingFileAppender 初始化失败、JVM exit=1，而代码只接受 `0|124`。修复：启动前 `mkdir -p /home/ruoyi/logs`；rc 判定放宽为 `0|1|124`（无 DB/Redis 环境连不上依赖主动退出属预期）。同时把 go/rust 的 `head` 也改 `sed` 防同类隐患。

### 4.2 self-hosted-ci

- backend `selfhost-canary.yml`（master）默认 `runner_label: wsl-k3s-api`——那是 api 仓库的 runner，backend 的是 `wsl-k3s`（历史成功 run 日志实证 `SELFHOST_CANARY_OK runner=wsl-k3s`）。修复：默认值改为 `wsl-k3s`。
- 两仓库 `self-hosted-ci.yml`（java-V3/jdk17/21/25 分支）build job 用 cloud runner、deploy job 用各自正确 label，文件层面无确定性 bug；历史失败 run 均为 push 事件旧配置遗留（jobs=0，文件级失败），当前已改为仅 workflow_dispatch。
- **环境限制**：查询时两仓库 self-hosted runner (`wsl-k3s`/`wsl-k3s-api`) 均离线（runners API 返回空），故 deploy 类 job 无法在此环境实机验证；这是基础设施问题，非 workflow 文件问题。
